
# **Q1. Уникальные рейсы и сортировка**
### **1. DISTINCT и GROUP BY**
Запросы

SELECT DISTINCT flight\_no

FROM flights

ORDER BY flight\_no;

и

SELECT flight\_no

FROM flights

GROUP BY flight\_no

ORDER BY flight\_no;

в данном случае возвращают **одинаковый итоговый набор данных**: 
### **2. Почему достаточно ORDER BY flight\_no**
В PostgreSQL направление сортировки по умолчанию — ASC, то есть по возрастанию.

Поэтому

ORDER BY flight\_no

эквивалентно

ORDER BY flight\_no ASC

Таким образом, регистр может влиять на порядок, а строки, отличающиеся только регистром, не обязательно будут расположены так, как ожидается при побайтовом сравнении.

# **Q2. Аэропорты и выручка за билеты**
### **1. Два билета одного пассажира**
Если один пассажир купил два разных билета на один рейс, например:

|**passenger**|**seat**|**amount**|
| :-: | :-: | :-: |
|100|10A|5000|
|100|10B|5000|

то COUNT(\*) посчитает **две строки**, то есть фактически два билета, а не одного уникального пассажира.

Поэтому если требуется количество именно пассажиров, следует использовать:

COUNT(DISTINCT passenger\_id)

А выручку можно считать:

SUM(amount)

То есть:

SELECT flight\_id,

`       `SUM(amount) AS revenue,

`       `COUNT(DISTINCT passenger\_id) AS passengers

FROM ticket\_flights

GROUP BY flight\_id;
### **2. Рейс без проданных билетов**
Если рейс есть в flights, но соответствующих строк в ticket\_flights нет, INNER JOIN исключит этот рейс из результата, потому что совпадающей строки в правой таблице нет.

Нужно использовать LEFT JOIN:

SELECT f.flight\_id,

`       `COALESCE(SUM(tf.amount), 0) AS revenue

FROM flights f

LEFT JOIN ticket\_flights tf

`       `ON tf.flight\_id = f.flight\_id

GROUP BY f.flight\_id;

LEFT JOIN сохраняет **все строки из flights**, даже если справа соответствий нет.

Для такого рейса SUM(tf.amount) будет NULL, поэтому используется:

COALESCE(SUM(tf.amount), 0)

чтобы получить 0.

# **Q3. Отменённые рейсы и города**
### **1. Аэропорт, из которого вообще не было рейсов**
Если в airports есть аэропорт, который вообще не встречается в flights, он действительно удовлетворяет условию «из этого аэропорта не было отменённых рейсов».

Например, с NOT EXISTS:

SELECT a.city

FROM airports a

WHERE NOT EXISTS (

`    `SELECT 1

`    `FROM flights f

`    `WHERE f.departure\_airport = a.airport\_code

`      `AND f.status = 'Cancelled'

);

Такой запрос вернёт и аэропорты, из которых не было **ни одного** рейса, потому что для них подзапрос не найдёт отменённых рейсов.

Можно использовать NOT IN, но он менее безопасен при наличии NULL:

SELECT city

FROM airports

WHERE airport\_code NOT IN (

`    `SELECT departure\_airport

`    `FROM flights

`    `WHERE status = 'Cancelled'

);

Для этой задачи предпочтительнее NOT EXISTS, поскольку он корректно работает с NULL.
### **2. Почему NOT IN опасен при NULL**
Проблема возникает, если подзапрос возвращает хотя бы один NULL.

Например:

city NOT IN ('A', 'B', NULL)

логически превращается в сравнение с неизвестным значением. В SQL используется трёхзначная логика: результат может быть TRUE, FALSE или UNKNOWN.

Условие WHERE пропускает только TRUE, поэтому наличие NULL может привести к тому, что строки не попадут в результат.

NOT EXISTS такой проблемы не имеет:

WHERE NOT EXISTS (

`    `SELECT 1

`    `FROM flights f

`    `WHERE f.departure\_airport = a.airport\_code

`      `AND f.status = 'Cancelled'

)

Здесь проверяется наличие конкретной подходящей строки. Если подходящей строки нет, EXISTS становится FALSE, а NOT EXISTS — TRUE.

**Вывод:** при подобных проверках NOT EXISTS обычно безопаснее, особенно если участвующие столбцы потенциально содержат NULL.

# **Q4. Места на борту и дубликаты**
### **1. Один пассажир получил два посадочных талона**
Если нужно вывести **уникальных пассажиров**, необходимо убрать дубликаты.

Например:

SELECT DISTINCT passenger\_id

FROM boardings;

Если используются дополнительные таблицы:

SELECT DISTINCT b.passenger\_id

FROM boardings b

JOIN ticket\_flights tf

`  `ON ...

Альтернативный вариант:

SELECT passenger\_id

FROM boardings

GROUP BY passenger\_id;

Оба варианта дают одинаковый результат с точки зрения набора уникальных passenger\_id.

Нельзя однозначно сказать, что DISTINCT всегда эффективнее GROUP BY или наоборот. PostgreSQL выбирает физический план самостоятельно. В зависимости от данных и условий он может использовать сортировку, HashAggregate и другие стратегии.

Поэтому эффективность нужно проверять конкретным:

EXPLAIN ANALYZE

...

Если нам требуется только удалить дубликаты и не выполнять дополнительные агрегатные вычисления, DISTINCT обычно лучше выражает смысл запроса.
### **2. Посадочный талон есть, а билет отсутствует**
Если запрос использует:

FROM tickets t

JOIN boardings b ON ...

то это INNER JOIN.

Пассажир, у которого есть посадочный талон, но нет соответствующего билета, **не попадёт в результат**, потому что для INNER JOIN обязательно наличие соответствующей строки в обеих таблицах.

Это также помогает обнаружить аномалию данных: посадочный талон существует, но связанного билета нет.

Если же нужно специально показать такие аномальные записи, потребуется другой тип соединения, например LEFT JOIN от boardings.

# **Q5. DDL и блокировки на живой таблице**
### **1. ALTER TABLE во время долгого SELECT**
Команда:

ALTER TABLE flights

ADD COLUMN weather\_data JSONB;

для изменения таблицы должна получить блокировку, совместимость которой с обычным SELECT отсутствует.

SELECT обычно получает ACCESS SHARE, а ALTER TABLE в данном случае запрашивает сильную блокировку таблицы — ACCESS EXCLUSIVE.

ACCESS EXCLUSIVE конфликтует с ACCESS SHARE.

Поэтому ситуация будет примерно такой:

Транзакция 1:

BEGIN;

SELECT COUNT(\*) FROM flights;

-- транзакция остаётся открытой

Транзакция 2:

ALTER TABLE flights ADD COLUMN weather\_data JSONB;

-- ждёт

Пока первая транзакция удерживает необходимую блокировку, ALTER TABLE будет ждать её завершения.

После:

COMMIT;

первая транзакция освобождает блокировку, и ожидающая DDL-команда сможет продолжить выполнение.
### **2. ADD COLUMN ... DEFAULT false в PostgreSQL 11+**
В PostgreSQL 11 появилась оптимизация для добавления столбца с постоянным значением DEFAULT.

Например:

ALTER TABLE flights

ADD COLUMN is\_delayed BOOLEAN DEFAULT false;

не требует физически переписывать всю таблицу только ради заполнения старых строк значением false.

PostgreSQL сохраняет информацию о значении по умолчанию в системных структурах и может логически считать старые строки имеющими это значение, пока строка не будет физически изменена.

Поэтому операция выполняется значительно быстрее и без полного прохода/перезаписи всех строк таблицы.

Если впоследствии выполнить:

ALTER TABLE flights

ALTER COLUMN is\_delayed SET DEFAULT true;

это изменит **DEFAULT для новых вставок**.

Существующие строки от этого автоматически не превратятся в true. Они сохранят прежнее логическое значение false (если не были изменены отдельно).

Новые:

INSERT INTO flights (...)

VALUES (...);

если не указать is\_delayed, будут получать true.
### **3. CREATE INDEX и блокировки**
Обычная команда:

CREATE INDEX idx\_flights\_status

ON flights(status);

во время построения индекса блокирует операции изменения таблицы в той мере, которая не позволяет обычным INSERT, UPDATE и DELETE свободно продолжать работу с таблицей.

Для production-таблицы можно использовать:

CREATE INDEX CONCURRENTLY idx\_flights\_status

ON flights(status);

CONCURRENTLY позволяет построить индекс с существенно меньшими блокировками, не блокируя обычные операции записи на всё время построения.

Однако есть компромиссы:

- индекс строится дольше;
- требуется больше ресурсов;
- операция выполняется в несколько этапов;
- CREATE INDEX CONCURRENTLY нельзя выполнять внутри обычной транзакции;
- при проблеме построения может остаться невалидный индекс, который потребуется обработать.

Поэтому для нагруженных production-таблиц CONCURRENTLY часто полезен, но он не является бесплатной заменой обычному CREATE INDEX.

# **Q6. Агрегация и NULL в вычислениях**
### **1. AVG и отменённые рейсы**
Запрос:

SELECT AVG(actual\_departure - scheduled\_departure)

FROM flights;

не будет учитывать строки, для которых выражение:

actual\_departure - scheduled\_departure

равно NULL.

Поскольку арифметическое выражение с NULL даёт NULL, отменённый рейс с отсутствующим actual\_departure не участвует в расчёте AVG.

Например, если задержки:

10 минут

20 минут

NULL

30 минут

то среднее считается по:

10, 20, 30

а не по четырём строкам.

Это означает, что AVG рассчитывает среднюю задержку **только среди рейсов, для которых задержку удалось вычислить**.

Если все значения выражения окажутся NULL, результат AVG тоже будет NULL.
### **2. COUNT(aircraft\_code) и COUNT(\*)**
Эти запросы:

SELECT COUNT(aircraft\_code)

FROM flights;

и

SELECT COUNT(\*)

FROM flights;

могут вернуть разные значения.

COUNT(\*) считает **все строки** таблицы.

COUNT(aircraft\_code) считает только строки, в которых:

aircraft\_code IS NOT NULL

Например, если в таблице 100 рейсов, но у 5 из них aircraft\_code = NULL:

COUNT(\*)              = 100

COUNT(aircraft\_code)  = 95

Если aircraft\_code объявлен как:

aircraft\_code ... NOT NULL

то NULL там невозможен, поэтому:

COUNT(aircraft\_code)

и

COUNT(\*)

дадут одинаковый результат.

Итак:

- COUNT(\*) → считает строки;
- COUNT(column) → считает только ненулевые значения column.
